Fleet Command Center: what changes, what breaks, and what stays

A plan for turning the working prototype into a four-company monitoring system — without replacing the thing that already works.

The question you asked

You don't need a parallel system. You need a rollback path.

Almost nothing here replaces what you have. Two files change; everything else is new files sitting alongside the old ones.

Building a second Grafana and a second database to test against would double the work and still wouldn't prove much — the risk isn't in the new parts, it's in the two existing files that get edited. Git already solves that, and better: the old version of each file stays one command away, permanently.

Nothing is ever guaranteed safe. But "safe" here means reversible in under a minute, and that's achievable. Here is every file the plan touches:

The safety procedure is three habits, not a second system: work on a branch, keep the old ingestion.py runnable so switching back is one command, and rehearse the full demo end-to-end at least a day before you present it.

The architecture, intuitively

Four jobs, and one of them is currently in the wrong place

Think of the system as four jobs handed off in sequence. Every piece of it does exactly one:

  • The senders — your LilyGO board and the simulated sensors. They measure and shout. They don't judge.
  • The post office — Mosquitto. It routes messages and never looks inside them.
  • The recorder — ingestion.py and Postgres. Writes things down and keeps them.
  • The watcher — Grafana. Reads what was written, decides what's alarming, raises the alarm.

That division is already almost right in your build. The single problem is that the recorder is currently also acting as the judge — and it throws away what it disapproves of before the watcher ever sees it.

Why this is the whole ballgame

You cannot raise an alarm about a reading you deleted. Every other improvement in this plan is worth having; this one is the difference between a system that alerts and a system that only appears to.

Multi-tenancy

Who owns a sensor becomes data, not code

Right now nothing anywhere records that a sensor belongs to Plymouth. The fix is a small devices table mapping each device to its company, its site, and the temperature band that company actually needs:

TRUCK-LILYGO-001 → Plymouth · Demo Bench2 – 6 °C
PLY-SIM-01…05 → Plymouth · Seattle, Tacoma2 – 6 °C
ALO-SIM-01…05 → Aloha · Honolulu, Kahului1 – 5 °C
NIK-SIM-01…05 → Nikky USA · Portland, Boise−23 – −18 °C
SNJ-SIM-01…05 → S&J · Spokane, Yakima0 – 4 °C

Two things follow from this, and they're the reasons it's worth a whole extra table.

Each company gets its own definition of "too warm"

Nikky USA hauls frozen goods at −23 to −18 °C. Plymouth hauls produce at 2 to 6 °C. A single global threshold cannot serve both — it would either scream at Nikky constantly or never notice Plymouth spoiling. One alert rule reads each device's own limits from this table, so all four companies are judged correctly by the same rule.

Adding a fifth company is a config edit, not a code change

Add the rows. The dashboard's company filter is built from SELECT DISTINCT company, so the new name appears in the dropdown by itself. The alert rules already join this table, so they cover the new sensors immediately. The only deliberate step is adding one Slack routing entry if that company wants its own channel.

And the device never gets to say who it belongs to

It would be simpler to have the firmware include "company": "Plymouth" in each message. Don't. A device that declares its own tenant can declare somebody else's, and once four customers share one database that's the difference between a bug and a breach. The device sends its ID; the server decides what that ID means.

Honest accounting

What you gain, what it costs

What you gain

  • Alerts that can actually fire — the core fix
  • Per-company temperature limits from one rule
  • Dead-sensor detection, which no threshold rule can ever catch
  • Survives a Postgres restart instead of silently dying
  • A new company is rows, not code
  • Grafana config in git, so the volume stops being irreplaceable
  • Real board and simulated fleet share one pipeline — the demo shows the true product

What it costs

  • Queries now need a join; slightly more to hold in your head
  • The device registry must be maintained — an unregistered device shows up with no company
  • Storage grows faster once readings stop being discarded
  • Staleness alerts need tuning or they cry wolf on every tunnel and dead zone
  • The Slack webhook is a secret to manage, and needs outbound internet from the VM
  • Provisioned config is read-only in the Grafana UI unless deliberately unlocked
  • More moving parts, and you are the only person who knows how they fit

What doesn't change

  • The telemetry table and every row already in it
  • Both Docker volumes
  • Mosquitto and its config
  • The MQTT payload shape your firmware already sends
  • Dashboards you've already built by hand
  • The overall shape you designed — this is a correction, not a redesign

The demo

Twenty simulated sensors, one real probe, and a glass of ice water

Four companies publish continuously in the background so the dashboard looks like a live operation rather than a test rig. Your LilyGO is the sixth Plymouth device and the only one you touch — which is what makes the moment land, because the audience watches a physical object change a number on a screen.

≈ 4 °CProbe starts in chilled water. Plymouth is green. All four companies nominal.
≈ 100 °CInto hot water. Temperature climbs through the 6 °C ceiling within seconds, the panel flips to alarm, and Slack fires.
≈ 0 °CInto ice water. Now it breaches the low limit — freeze damage is a real spoilage mode, and it proves the rule works in both directions.
risingMeanwhile an Aloha unit in Honolulu drifts up on its own. A second company alarms without you touching anything.
silenceAn S&J unit stops reporting entirely. The staleness alert catches what a temperature rule structurally cannot.

Two things to rehearse, not discover on stage

Room air is already an alarm. At roughly 20 °C, your probe sitting on the table is far above Plymouth's 6 °C ceiling. If you want to open on a calm green dashboard, the probe has to start in chilled water — not in your hand.

Boiling water needs a waterproof probe and a wider ceiling. The bare sensor and its cable aren't rated for it, and ingestion.py currently discards anything above 101 °C — so boiling water would be thrown away as implausible. Hot tap water at 50–60 °C is dramatic enough and far safer for the hardware.

Sequence

The plan, in the order it has to happen

01
Back up the firmware — before anything else
The code running on your board exists in exactly one place and is not in git. Every hour it stays that way is a working device configuration you'd have to re-derive from scratch. This blocks everything else.
02
Create the devices table and register all 21 sensors
Purely additive. Nothing existing is touched, and it's what every later query depends on.
03
Repair ingestion.py
Reconnect to Postgres on connection loss; reject only the physically impossible; record what was rejected instead of discarding it silently. Old version stays one command away.
04
Finish and run the fleet simulator
Already about 90% written. Backfill a day of history so the dashboard opens with a populated view rather than a blank one.
05
Build the Grafana pane and the three alert rules
Temperature excursion, staleness, low battery — all grouped by company and site.
06
Wire Slack and prove one alert end to end
Do this early. A blocked outbound connection from the VM is the failure most likely to surface on demo day.
07
Firmware demo mode, then full dress rehearsal
Short publish interval instead of the hour-long sleep, then run the entire demo start to finish while there's still time to fix what breaks.

Logistics

Access, and what I'd need from you

On the firmware and your host machine

Yes — opening a session on the host would genuinely help. The board's source lives there, the USB port is there, and right now every firmware change is you copying code between machines by hand. But there's a firm precondition: the firmware gets committed to git first. Editing the only copy of something is how the only copy gets lost.

On flashing: I'd want to confirm with you before each flash rather than doing it silently. Writing to a physical device is the one action here that isn't a git checkout away from being undone, and a demo board that won't boot the night before is a bad way to learn that.

01

Slack webhook URL — you create it at api.slack.com in your own workspace; it takes about two minutes and needs workspace-admin rights. I never need Slack access myself: Grafana does the sending, not me. I can write the config with a placeholder if it'll take time to get approved.

02

One Slack channel or four? One is simpler and fine. Four makes per-company routing visible in the demo, which is more convincing to a customer, and costs about ten extra minutes.

03

Confirmation I can edit ingestion.py and docker-compose.yml — the compose change adds a config mount and restarts only the Grafana container. Both volumes are untouched.

04

Whether the VM can reach the internet — if a proxy or firewall blocks outbound HTTPS, Slack won't work and we should find that out in week one, not on demo day.

05

Your call on Grafana config — I'd suggest provisioning the plumbing (datasource, Slack routing) as code, and building dashboards and alert rules in the UI where you can freely experiment, then exporting them to files once you're happy.
